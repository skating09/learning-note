一、BSW的CAN功能详解

COM：从应用层传下来数据首先就进入这里，应用层无需关心收发的数据是通过什么总线传输的，应用只需要将它传输给COM即可。同样，COM上传的数据也是很单纯的数据里面没有这个数据是什么总线上传的这样无意义的信息，应用层关心的是这个数据的实际意义和数据大小。所以COM主要就起了一个信号接口和网关的作用。

PDU Router:PDU-Protocol Data Unit:协议数据单元。功能是将COM下发的信号数据分配到相应的协议总线上去；或者将不同的协议变成同一信号上传给COM；

IPDU Mux:用于解析一些特殊的协议，比如CAN FD或者用户自定义的一些协议，作用是统一CAN ID，不同信号Layout

CAN Tp:分包数据传输与错误检测，一般来说只有在诊断的时候才会使用。

CAN If(CAN Interface)：与硬件已经无关了，这个Interface主要可以配置收发队列；组帧(FlexRay);管理时间触发总线的调度表(LIN,FlexRay)

CAN Driver:就是MCAL中对主芯片上CAN模块的驱动封装

Trcv Driver: Trcv-Transceiver 的缩写，就是收发器驱动的意思。如果是外置CAN收发器，这里就要用到Trcv Driver 驱动

1.CAN分层活动


从AUTOSAR架构上来说，一个完整的CAN通信的过程涉及到了包括硬件、AUTOSAR中间件和上层应用层软件；

    在硬件部分来说，涉及到的是CAN总线和CAN收发器；

    软件部分涉及到的概念是MCAL(微控制器抽象层)、BSW(基础软件层)、RTE(实施运行环境)、APPL(应用层)等。其中MCAL部分用到了通信驱动模块，而BSW部分使用到了通信服务模块和通信硬件抽象模块；

1 交互层
IPDU multiplexer:协议数据单元复用模块

COM：COMMUNICATION通信模块

DCM：诊断通信管理模块(Diagnostaic Communication Manager)

PDUR:Protocol Data Unit Router PDU路由器

2 网络层
CAN TP：CAN Transport Layer

CAN TP提供的服务包括：传输方向的数据分割、接收方向的数据重组、数据流控制、检测分割会话中的错误、传输取消接收取消

J1939 TP：给予J1939协议的CAN TP，J1939Tp模块实现了SAEJ1939标准中的两种数据传输方式BAM和CMDT

3 数据链路层
CAN Interface:CAN 接口层(CanIf)是访问CAN总线的标准接口

4 物理层

CAN Driver：CAN驱动，可以实现对CAN控制器的初始化、发送/接收CAN报文、对接收报文的指示与对发送报文的确认、唤醒检测、溢出和错误处理等功能。

CAN Controller:CAN 控制器

CAN Transceiver Driver:CAN收发器驱动程序抽象了CAN收发器硬件。它为较高层提供了一个独立于硬件的接口。它利用MCAL层的API从ECU布局中抽象出来，访问CAN收发硬件。

Message:报文

2.收发控制流(节点发送数据举例)

  • 应用层Send一个数据进COM

  • COM写信号进PDU Buffer中

  • PDU被PDU Router立刻发送或按周期发送(每个PDU都有一个独立的ID)，之后PDU Router辨认总线种类，并把PDU发向不同的下级模块

  • Interface根据不同的通道，把报文写入不同的队列

  • Driver根据报文的优先级立刻发送报文

3.报文帧详解

ECU 在通信和诊断中应使用标准帧。ECU 不可发送和响应远程帧、扩展帧，当总线上有远程帧和扩展帧发送时，ECU 接收后不做处理且不发出错误帧。

4.报文发送方式

周期型（Cycle）
报文按照一定周期时间发送，周期时间参考矩阵中“报文周期时间”参数。例：报文发送类型定义为 Cycle，报文周期时间定义为 T。
事件型（Event）
当事件发生时，报文立即发送，报文发送次数和发送时间间隔参考矩阵中的“报文快速发送的次数”和“报文发送的快速周期”参数。
使能型（Ifactive）
当报文中所有信号均为使能型信号，且某一信号等于使能值时，报文进行发送，发送时间间隔参考矩阵中的“报文发送的快速周期”；当使能信号均从使能值切换为非使能值时，报文继续发送几帧，发送的次数和时间间隔参考矩阵中的“报文快速发送的次数”和“报文发送的快速周期”参数。信号的非使能值参考矩阵中的“非使能值”参数。

5.报文数据长度及填充

CANFD 网络上，数据帧的数据长度 DLC 可以是 8/12/16/20/24/32/48/64, 供应商须按照通信矩阵中定义的标识符和 DLC 进行报文的发送，其它未定义的标识符和 DLC 不应发送。当 ECU 接收到 DLC 不同于预定义的数据帧时，应忽略该报文，并对 CAN 总线不产生任何影响。
报文数据场的字节填充格式采用 Motorola 格式，信号的起始位从最低有效字节（LSB）的最低有效位（lsb）开始。应用报文中未使用（预留）的字节默认填充 0x00，未使用（预留）的信号位默认填充 0x0。
Busoff
避免 ECU 因自身故障影响其它正常节点通信，ISO11898-1 规定每个 CANFD 控制器都有一个发送错误计数器和接收错误计数器。
主动错误状态（error active）：节点正常参与通信，当检测到错误时，发送主动错误标志。
被动错误状态（error passive）：节点正常收发报文，当检测到错误时，发送被动错误标志。
总线关闭状态（bus off）：节点因总线故障或自身严重问题进入总线关闭状态，该状态下无数据收发。

节点发生 Busoff 时，先快恢复再慢恢复。连续发生 5 次 Busoff 快恢复后，若此时又发生 Busoff就进入慢恢复

6.故障

网络相关的诊断包括工作电压诊断、总线 Busoff 故障诊断、节点丢失故障诊断、报文错误故障诊断、报文 Checksum 校验错误诊断、及报文计数器错误诊断。当 ECU 上电或被网络管理报文唤醒 T_DiagStart 后，ECU 开始网络相关的诊断。当 ECU 工作电压从欠压或过压恢复到正常诊断电压范围内，需从电压恢复时刻开始 T_DiagRecover 时间内恢复诊断功能。

Busoff 故障故障记录条件：诊断功能开启情况下，当 ECU 连续发生 Busoff 8 次，且没有报文成功发送，需记录 Busoff DTC。故障恢复条件：ECU 成功发送一帧报文后，即认为 Busoff 故障恢复。

节点丢失故障 ECU 需对与自身功能处理或物理总线直连的相关 ECU 进行节点超时监测。ECU 供应商可选择所接收的相关 ECU 的任意一条周期最小的报文进行监控，或选择任意一条对功能影响较大的关键周期型（或周期事件型）报文进行监控，或选择多条（或所有）的周期型（或周期事件型）报文进行监控。当选择多条（或所有）的周期型（或周期事件型）报文进行监控时，应在所有监控报文都超时后方可记录节点丢失故障。

报文错误故障（可选）节点应能够检测报文自身故障，如位错误、CRC 错误、界定符错误等。

报文 Checksum 校验错误报文 Checksum 算法，依据不同车型要求另行定义。

总线故障
本地故障网络中所有 ECU 必须有容错性能。1) ECU 任何内部错误都不能影响总线通信（e.g.发送错误帧或者把总线钳位在“显性”状态）；2) 总线错误帧不能影响 ECU 内部功能，也不能把 ECU 置于不安全状态；3) ECU 启动期间，不应干扰其他 ECU 的正常通信；
全局故障总线发生以下全局故障时，CAN 通信通常会受到干扰。

总结

以上就是 Davinci Cfg Configurator 中关于 Can 模块的配置介绍。
这个模块主要进行 Can 控制器相关参数和 Can 模块的 Tx 和 Rx 的 MailBox 配置，至于 CanGeneral 的配置，一般保持默认即可。另外关于轮询式 Can 报文处理的周期定义，仅在配置为轮询式处理方式时才需要，对于配置为中断式的，空置即可。
这个模块可以理解为是 AUTOSAR 架构下 Can 通信的最低层（暂不考虑 MCAL），直接与 CanBus 交互。

三、项目实战CAN收发链路C代码实现

1 宏观视角AUTOSAR 的 CAN 通信分层


在深入代码前，我们先看一眼底层的“快递分发”流程（自下而上）：

1 CanTrcv / CanDrv（物理层 & 硬件驱动层）：负责把物理总线上的高低电平（如 2.5V/3.5V）翻译成数字信号（0 和 1），并按帧存入单片机的 CAN 邮箱（Mailbox）。
2 CanIf（CAN 接口层）：屏蔽不同单片机硬件的差异，向上一层提供统一的 CAN 帧（PDU）处理接口。
3 PduR（PDU 路由层）：相当于快递分拣中心。它看一眼报文：如果是诊断请求，扔给 Dcm 模块；如果是网络管理报文，扔给 CanNm；如果是普通业务数据，扔给 Com 模块。
4 Com（通信服务层，核心！）：负责把一整帧报文（如 8 字节或 64 字节）拆解/打包成一个个具体的信号（Signal），比如规定第 3 个字节的前 4 位代表电压。
5 App / ComUsr（应用层 / 通信用户接口）：负责执行安全校验、超时监控，并把原始数据转换成业务需要的物理值，最终去做决策。

2 底层 API 调用级的完整流转路线图

我们以经典的 CAN 通信 为例，分“发送（Tx）”和“接收（Rx）”两条链路来剖析。

报文发送流程（Tx Flow：从应用层到物理总线）

发送的核心思想是：“异步解耦”。应用层只要把数据往 Buffer 里一塞就可以不管了，真正把数据搬运到硬件上发出去的，是底层的周期任务（MainFunction）。

完整函数流转序列：

1 App / ComUsr 层：写入缓存

动作：在 ComUsr_CDU_DCDC_1_0x467_100_COMBO_GWAY_Tx 任务中调用 Com_SendSignal() 或 Rte_Write()。
底层行为：这步不会触发报文发送！它仅仅是把数据（比如 138 这个电压值）写到了 Com 模块的内部 RAM 缓存（Shadow Buffer）中。

2 Com 模块：周期打包（触发点）

动作：系统底层的 OS 会周期性（比如每 5ms 或 10ms）调用 Com_MainFunctionTx()。
底层行为：这个大管家会去查所有的发件箱。它发现 0x467 这个 PDU（Protocol Data Unit，即 CAN 帧）的 100ms 发送周期到了，于是它把之前所有 Com_SendSignal 填进来的零碎 Signal 拼装成一个完整的 8 字节 PDU。
向下传递：拼装完成后，Com 调用下层接口： → \rightarrow → PduR_ComTransmit(PduId, &PduInfo)

3 PduR 模块：简单路由

动作：PduR (PDU Router) 发现这个 PDU 的目的地是 CAN 总线。
向下传递：直接透传调用： → \rightarrow → CanIf_Transmit(CanIf_PduId, &PduInfo)

4 CanIf 模块：软硬件映射

动作：CanIf (CAN Interface) 负责把纯软件的 PDU ID（比如 ID 5）映射到物理的 CAN Controller 和真实的 CAN ID（0x467）。如果有硬件发送队列，它还会做软件缓存。
向下传递：调用处于最底层 MCAL 的硬件驱动： → \rightarrow → Can_Write(Hth, &PduInfo)

5 Can 模块 (MCAL) 与硬件：填入邮箱

动作：Can_Write 函数会直接操作 AURIX 单片机的寄存器（MultiCAN+ 模块）。它将 0x467、DLC（8）以及那 8 个字节的 Payload，直接写入到芯片硬件的 Tx Mailbox（发送邮箱）中。
发送：硬件仲裁通过后，这帧报文化作高低电平，飞向总线。

6 Tx Confirmation（发送回执 - 自下而上）

动作：当报文成功发到总线上后，单片机触发一个 硬件发送中断 (Tx ISR)。
流转：Can_TxInterrupt() → \rightarrow → CanIf_TxConfirmation() → \rightarrow → PduR_TxConfirmation() → \rightarrow → Com_TxConfirmation()。
结果：Com 模块知道“快递已签收”，清除发件标志，准备下一个周期的发送。

报文接收流程（Rx Flow：从物理总线到应用层）

接收的核心思想是：“中断打底，任务收尾”。底层的中断只负责把数据抢救到 RAM 里，解包和处理全靠 OS 的周期任务。

完整函数流转序列：

1 硬件与 Can 模块 (MCAL)：硬件过滤与中断

动作：总线来了一帧 0x191 报文。AURIX 的 MultiCAN+ 硬件过滤器发现这是自己需要的 ID，将其存入 Rx Mailbox（接收邮箱），并立刻触发一个 硬件接收中断 (Rx ISR)。
向上传递：中断服务函数快速读取寄存器，把数据搬进局部变量，然后调用： → \rightarrow → CanIf_RxIndication(Hrh, CanId, Dlc, PduInfoPtr)

2 CanIf 与 PduR：验证与分发

动作：CanIf 确认数据长度无误后，把硬件的 HRH（硬件句柄）转换成软件的 RxPduId。
向上传递： → \rightarrow → PduR_CanIfRxIndication(PduId, PduInfoPtr) → \rightarrow → Com_RxIndication(PduId, PduInfoPtr)

3 Com 模块：中断上下文的快速存缓存

动作：此时我们依然处于（或刚刚退出）中断上下文中！因此 Com_RxIndication 绝对不会去做复杂的浮点数运算。它只做一件事：把这 8 个字节的报文拷贝到 Com 模块的内部 Rx Buffer 中，并立起一个“有新数据到达”的 Flag。
(注：如果配置了 Callout，您的 E2E_0x191_VCU_CDU_3…Rx_PDUCallback 会在此刻被调用，去校验 CRC)。

Com 模块：周期性解包（后台管家）

动作：OS 周期性调度 Com_MainFunction_Rx()。
底层行为：它扫描到 Rx Buffer 里有新鲜的 0x191，于是按照 DBC 矩阵的定义，把这 8 个字节拆成一个个 Signal。同时它还会刷新这个报文的 Timeout 定时器（防止触发掉线故障）。

App / ComUsr 层：取走数据

动作：您的 10ms 周期任务 ComUsr_vidQMRunnable_10ms 开始运行。
获取：调用 Com_ReceiveSignal() 或 Rte_Read()。
结果：此时，您拿到的是 Com 模块早就为您拆解并准备好的、热乎的数据。接下来您乘以分辨率（Factor），就得到了 14.2V 的物理值。
三、 图解：一图胜千言
我们可以把这个过程想象成一个“跨国邮政系统”：

为什么 AUTOSAR 要搞得这么复杂？
看到这里，您可能会觉得：“以前裸机开发，我直接在 CAN Rx 中断里解析数据不香吗？为什么要绕 5 层？”

AUTOSAR 这么设计是有其深刻原因的：

防阻塞：CAN 中断的优先级极高，如果在中断里做解包、乘除法甚至 E2E 校验，一旦总线负载率达到 80%，单片机连 OS 任务都调度不过来了。
硬件解耦：今天项目用的是英飞凌 TC364（CAN），明天如果要移植到瑞萨芯片，甚至通信介质换成 LIN（如您项目中看到的 Lin_17_AscLin）或以太网（Eth），应用层代码连一个标点符号都不需要改！底层只需替换 CanDrv 为 LinDrv，上面的 Com 和 PduR 依然如常工作。

3 应用层完整详细接收流程（Rx Flow）

假设现在 VCU（整车控制器）通过 CAN 往 CDU 发送了一帧指令报文 VCU_CDU_3 (ID: 0x191)，周期是 10ms。

第 1 步：底层送达与 E2E 安全校验 (Callout)
为了符合主机厂的 ISO 26262 功能安全规范，关键报文通常带有 E2E（End-to-End）保护。当底层的 Com 模块收到 0x191 报文，准备拆包之前，会先触发一个回调函数让您检查这包“快递”有没有被拆过或者是不是旧包裹。

FUNC(boolean, COM_APPL_CODE) E2E_0x191_VCU_CDU_3_oPublic_CAN_a11ed0da_Rx_PDUCallback(...)
{
   // 1. 提取对方发过来的 滚动计数器(Rolling Counter)
   Loc_u8TempCounter = (PduInfoPtr->SduDataPtr[COMUSR_VALUE_1] & COMUSR_MASK_0x0F);

   // 2. 调用 AUTOSAR 标准的 E2E_P01Check 进行 CRC 校验和计数器连续性检查
   (void)E2E_P01Check(&ComUsr_P01Crc, &ComUsr_astrRxCntDara[ComUsr_enuID_0x191].ComUsr_P01RxCounter, ...);

   // 3. 如果校验失败（比如被人篡改了，或者掉帧了），记录错误状态
   if (E2E_P01STATUS_WRONGCRC == ComUsr_astrRxCntDara[...].Status) {
      ComUsr_astrRxDataInfo[...].CRCErrorStatus = TRUE;
   }
   return TRUE;
}

第 2 步：提取信号 (Signal)
E2E 校验通过后，工程里每 10ms 调度一次的 XX_vidQMRunnable_10ms 任务中，会去提取这帧报文里具体的信号。

FUNC(void, ComUsr_CODE) ComUsr_VCU_CDU_3_0x191_10_Rx(void)
{
   // 使用标准 API Com_ReceiveSignal，从底层 Com 模块的缓存中把所需的信号值抠出来
   (void)Com_ReceiveSignal(ComConf_ComSignal_VCU_DCDCVoltageSetPoint_oVCU_CDU_3_oPublic_CAN_66d817f9_Rx, &ComUsr_u8VcuDCDCVoltageSetPoint);

第 3 步：转换成物理值 (Scaling)
总线上跑的只能是无符号整数（如 0~255）。主机厂的 DBC（通信矩阵）会定义每个信号的 分辨率（Factor） 和 偏移量（Offset）。应用层拿到原始值后，要算成物理值：

   // 物理值 = 原始整数 * 分辨率(0.1) + 偏移量(0)
   // 比如 VCU 要求设定电压，发来原始值 142，乘 0.1 后，就是 14.2 伏特
   ComUsr_f32VcuDCDCVoltageSetPoint = ((float32)(ComUsr_u8VcuDCDCVoltageSetPoint)) * COMUSR_ACC_0P1 + COMUSR_OFFSET_0;
}

第 4 步：报文丢失监控 (Timeout Monitoring)
如果线束断了，VCU 不发报文了怎么办？肯定不能一直用旧的 14.2V 去执行输出。 如果定时器发现太久没收到 0x191，就会向 DEM（诊断事件管理模块）上报故障：

   ComUsr_MsgLostHandler(&ComUsr_astrRxDataInfo[ComUsr_RxDataInfo_0x191], \
      (Dem_EventIdType)(DemConf_DemEventParameter_Lost_Communication_With_VCU),\ // 报 U014087 通信丢失故障
      &ComUsr_pstrTimer[TMR_COMUSER_VCU_COM_1_LOST_MSG_490MS]);

状态机一旦查到这个故障，就会立马跳进 FAULT 或 STANDBY 状态，确保整车安全。

4 应用层完整详细发送流程（Tx Flow）

现在反过来， CDU 自己测量到了 DCDC 模块输出的低压侧电压，需要打包成一帧名为 CDU_DCDC_1 (ID: 0x467) 的报文发给 VCU。

第 1 步：物理值反算成原始值
在 100ms 发送任务 ComUsr_CDU_DCDC_1_0x467_100_COMBO_GWAY_Tx 中，先去取真正的物理电压（比如内部测量到的是 13.8V），除以精度反算成无符号整数（变成 138）：

   ComUsr_f32DcdcLvSideVolt   = AnPhyCalcSafe_f32DCDCLvU; // 取底层模拟采集算出来的实际电压物理值
   ComUsr_u16DcdcLvSideVolt   = (uint16)((ComUsr_f32DcdcLvSideVolt) / COMUSR_ACC_0P1); // 除以0.1变整数

第 2 步：硬性限幅保护 (Clamping) —— 主机厂极其看重！

这也是量产代码和玩具代码的区别。如果硬件 ADC 传感器坏了，读到了一个 10000V 的荒谬值，除以 0.1 直接发出去，会导致接收方（比如仪表的里程续航计算）彻底崩溃。因此，发出去的信号必须卡在 DBC 规定的最大/最小值范围内。

   // 限制最大值绝不能超过 253 (即 25.3V)
   ComUsr_u16DcdcLvSideVolt   = MATHSRV_udtMIN(ComUsr_u16DcdcLvSideVolt, COMUSR_VALUE_253);

第 3 步：送入 Com 缓存
把限制好的安全整数交回给底层：

   (void)Com_SendSignal(ComConf_ComSignal_DCDC_LvSideVolt_oCDU_DCDC_1_..., &ComUsr_u16DcdcLvSideVolt);

注意： 调用 Com_SendSignal 并不会立刻就把报文发到 CAN 线上！它仅仅是把 138 这个值写到了 Com 模块的内存 Buffer 里。底层的 Com 模块自己有一个定时器，只要这帧报文配置的是 100ms 发送周期，时间一到，Com 就会把 Buffer 里拼好的这一整包 8 字节一起打出去。
第 4 步：发车前的最后动作（E2E 打包加密）
在底层真正把报文射出单片机前的一瞬间，会再调用您的 Tx Callout。在这里给包裹“贴上自己的防伪封条”：

FUNC(boolean, COM_APPL_CODE) E2E_0x467_CDU_DCDC_1_oPublic_CAN_a644bfb8_Tx_PDUCallback(...)
{
   // 1. 根据当前报文Buffer里的最新数据，计算出一个新的 CRC 校验和
   E2E_P01Protect(&ComUsr_P01Crc, &ComUsr_P01TxCounter, (PduInfoPtr->SduDataPtr+(8 * Loc_u8IsCrcByte)));

   // 2. 自己的滚动计数器加 1，告诉别人这绝对是一帧最新的报文（0~14循环）
   Stic_u8ID0x467Cntr = Stic_u8ID0x467Cntr + 1u;
   if(COMUSR_COUNTVALUE_15 == Stic_u8ID0x467Cntr) {
      Stic_u8ID0x467Cntr = 0u;
   }
}

这步完成后，这帧数据就顺着 PduR -> CanIf -> CanDrv，最终化作物理线束上的电平信号飞向了 VCU。在应用层，我们往往只需要调用 Com_SendSignal 和 Com_ReceiveSignal。
